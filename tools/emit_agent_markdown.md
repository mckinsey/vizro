# Adopt agent-facing Markdown in Kedro

This guide explains how Kedro can publish a clean, URL-addressable Markdown twin of every Zensical documentation page.

## What to copy

Copy [`emit_agent_markdown.py`](emit_agent_markdown.py) into Kedro's repository, for example at:

```text
tools/emit_agent_markdown.py
```

The script is deliberately standalone. Keep project-specific settings in the build command rather than editing the Python file. This makes future updates a one-file copy from Vizro.

The canonical upstream copy is:

```text
https://github.com/mckinsey/vizro/blob/main/tools/emit_agent_markdown.py
```

## Add dependencies

Add these packages to the environment that builds Kedro's documentation:

```text
beautifulsoup4>=4.13.0
markdownify>=1.2.0
```

They are build-time dependencies only; they do not need to be added to Kedro's runtime package dependencies.

## Add the post-build step

Run the script immediately after `zensical build`:

```shell
zensical build --clean
python tools/emit_agent_markdown.py --site-dir=site
```

For every Zensical page, this produces both URL shapes commonly guessed by agents:

```text
<path>/index.md
<path>.md
```

The root page produces `/index.md`. Links in generated Markdown remain canonical links to the normal documentation pages.

## Configure Kedro-specific behavior

The base command works without project-specific configuration. Add only the options Kedro needs.

### Exclude standalone HTML

Use `--exclude` for visual or hand-written HTML pages that do not use the standard Zensical documentation DOM:

```shell
--exclude=path/to/standalone/index.html
```

Paths are relative to `--site-dir`. Repeat the option for multiple pages. Do not exclude ordinary Zensical pages.

### Add a canary

Choose one substantial page whose content is generated from a directive such as mkdocstrings. The canary catches a Zensical DOM change that leaves generated Markdown present but unexpectedly empty:

```shell
--canary=reference/api/index.html
```

The default minimum size is 10,000 characters. Override it if appropriate:

```shell
--canary=reference/api/index.html --canary-min-chars=5000
```

### Add agent discovery links

If Kedro publishes `llms.txt` or a full documentation bundle, advertise them in the generated frontmatter:

```shell
--agent-docs='Index: https://docs.kedro.org/en/stable/llms.txt; full documentation: https://docs.kedro.org/en/stable/llms-full.txt'
```

Omit this option until those URLs exist.

A complete command might therefore look like:

```shell
python tools/emit_agent_markdown.py \
  --site-dir=site \
  --exclude=path/to/standalone/index.html \
  --canary=reference/api/index.html \
  --agent-docs='Index: https://docs.kedro.org/en/stable/llms.txt; full documentation: https://docs.kedro.org/en/stable/llms-full.txt'
```

## CI validation

Generation automatically runs all validation. To validate an existing build without rewriting it, rerun the same command with `--check`:

```shell
python tools/emit_agent_markdown.py \
  --site-dir=site \
  --canary=reference/api/index.html \
  --check
```

Use exactly the same `--exclude`, `--canary`, `--canary-min-chars`, and `--agent-docs` options for generation and checking.

The checks cover:

- a Markdown twin for every detected documentation page;
- no raw HTML, code-line anchors, or navigation text;
- a non-empty canary page.

## Add a local Hatch preview command

Zensical's development server rebuilds the HTML itself, bypassing the post-build Markdown step. Keep that hot-reloading command for normal documentation editing and add a separate static preview command:

```toml
[envs.docs.scripts]
serve-markdown = ["build", "python -m http.server {args:8000} --directory site"]
```

Here, `build` is the Hatch script containing `zensical build` followed by `emit_agent_markdown.py`. Run the preview with:

```shell
hatch run docs:serve-markdown
```

The Markdown pages are then available without a Read the Docs version prefix, for example:

```text
http://localhost:8000/reference/api.md
http://localhost:8000/reference/api/index.md
```

This command serves a completed static build and therefore does not hot-reload. Stop it, rebuild, and restart it after changing the documentation.

## Verify the deployment

On a preview deployment, check:

1. `/index.md` returns HTTP 200.
2. Both `<page>/index.md` and `<page>.md` return HTTP 200.
3. The response content type is `text/markdown`.
4. A page generated by mkdocstrings contains its expanded API content.
5. Mermaid diagrams remain fenced as `mermaid`.
6. Internal links point to canonical HTML page URLs.

Read the Docs already serves `.md` files as `text/markdown; charset=utf-8`, without a download header, so no additional content-type configuration should be necessary.

## Keeping the copies aligned

Treat Vizro's script as the upstream implementation:

1. Keep Kedro-specific values in its build configuration.
2. Avoid local edits to the copied Python file.
3. When Vizro changes the script, replace Kedro's copy and run its documentation build and checks.

This intentionally duplicates one small file across the repositories without creating another package or release process.
